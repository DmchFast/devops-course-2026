# Подготовка к контрольной работе №4

## 1. Когда я выберу rebase, а когда merge? Почему?

**Rebase** - для своих локальных feature-веток, которые ещё не пушились.
Причина: даёт линейную, читаемую историю, без лишних merge-коммитов.
Идеально подходит, когда нужно «подтянуть» свежий main в свою ветку
перед созданием Pull Request.

**Merge** - для публичных веток (main, develop, release) и для случаев,
когда важно сохранить факт параллельной разработки.
Причина: не переписывает историю, безопасен, не требует force-push.
Если коллеги уже работают с веткой. Только merge, не rebase.

**Правило:** rebase - для локального «причёсывания», merge для интеграции
в публичные ветки.

## 2. Что произойдёт, если сделать rebase публичной ветки, с которой работают коллеги?

Rebase **пересоздаёт коммиты** с новыми хешами. Если ветка уже была
опубликована и коллеги её склонировали, то после твоего force-push
у них окажется «устаревшая» история с прежними хешами.

Последствия:
- Их `git pull` будет конфликтовать или создавать дубликаты коммитов.
- Им придётся делать `git reset --hard` на новую историю — потеряют
  свои локальные изменения, если не сохранили их заранее.
- Возможна полная путаница в истории проекта.

**Главное правило:** never rebase public branches не делать rebase
публичных веток. Если очень нужно надо предупредить всю команду.

## 3. Зачем нужен multi-remote и в каких реальных сценариях он применяется?

Multi-remote позволяет одному локальному репозиторию иметь несколько
удалённых адресов (и fetch, и push по отдельности).

**Реальные сценарии:**
- **Зеркалирование (mirror/backup):** основной репозиторий на GitHub,
  резервная копия на GitLab (на случай падения одной из платформ).
- **Open-source:** внутренний корпоративный репозиторий + публичное
  зеркало на GitHub для сообщества.
- **Fork + upstream:** работа с форком и оригинальным репозиторием
  одновременно (классический сценарий в open-source).
- **Миграция платформ:** временный параллельный push в старый и новый
  хостинг, пока команда полностью не переедет.
- **CI/CD в разных системах:** один и тот же код должен попадать
  в GitHub Actions и GitLab CI одновременно.

Настройка: `git remote set-url --add --push origin <URL2>` — добавляет
второй push-адрес к origin.
